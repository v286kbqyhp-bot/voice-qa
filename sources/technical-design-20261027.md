# P003 小可真机语音自动化测试技术方案

- 编写日期：2026-10-27
- 文档状态：技术设计，尚未实现、接入设备或验证运行效果。
- 使用场景：川哥发来测试用例后，由测试电脑完成说话、等待、插话、录音、分析和回执整理。
- 采证方式：连续录音 + 实时设备日志，不要求录视频。
- 本文示例来源：[2026-10-26 测试用例与回执模板](P003_SEARCH_CANARY_DEVICE_TEST_RECEIPT_20261026.md)。后续收到新用例时，以新文件的步骤、顺序、预期和模板为准。

## 1. 最终做成什么

测试人选好设备、导入川哥发来的用例，启动一次测试。Mac 提前把需要说的话合成为 TTS 音频，再根据设备日志和麦克风听到的声音，在合适的时候播放。小可通过自己的麦克风接收这些声音，正常完成唤醒、识别、搜索和回答。

测试电脑全程录音。每轮结束后，系统整理“Mac 说了什么、小可实际回答了什么、何时停止或退出”，按用例判定结果，再按川哥提供的模板生成 Markdown 回执和证据包。

核心分工：**日志帮助决定什么时候说话；录音证明小可实际有没有说、说了什么。** 日志中的合成成功、下发成功、播放回调，都不能单独证明用户听到了声音。

自动化覆盖的是桌面上的真机声音测试。屏幕字幕、灯光实际变化、外观状态等不能仅凭录音证明，仍需相应传感器或测试人补充观察。本文不要求为了这些项目录制视频。

## 2. 从收到用例到交付回执的整体流程

```text
川哥发来测试用例、预期、版本信息和回执模板
    ↓
保存原文，提取用例、话术、顺序、会话要求和判定条件
    ↓
生成结构化测试计划，检查是否存在歧义或缺失条件
    ↓
核对设备、安装版本、日志连接、音频输入输出和搜索额度
    ↓
提前生成全部 TTS 音频，检查可播放、文本正确、设备能听清
    ↓
启动连续录音和日志采集，建立统一时间线
    ↓
执行每一步：等待条件 → 播放话术 → 观察回应 → 判断下一步
    ↓
每轮结束后：ASR 转写 → 区分说话者 → 对齐日志和声音 → 判定
    ↓
汇总覆盖情况、失败现象、重复次数及待确认项
    ↓
严格按原模板生成 Markdown 回执，附录音片段和日志索引
    ↓
测试人复核待确认项，将本地证据包交给川哥
```

| 阶段 | 系统做什么 | 产物 |
| --- | --- | --- |
| 接收用例 | 保存原文、模板和文件指纹，记录来源版本 | 原始文件、来源清单 |
| 编排计划 | 提取步骤，明确何时说话、说什么、等什么 | `cases.yaml` |
| 准备设备 | 核对身份、版本、日志、音频、额度 | `run_manifest.json` |
| 合成话术 | 生成独立音频并建立文本映射 | `tts/`、音频清单 |
| 执行测试 | 根据事件调度播放，同时连续录音、抓日志 | 原始录音、原始日志、播放记录 |
| 分析证据 | 转写、区分说话者、建立实际对话和判定 | `transcript.json`、`results.json` |
| 编写回执 | 按原模板填字段，链接证据 | `receipt.md`、证据包 |

## 3. 如何把川哥的文档变成可执行用例

### 3.1 保留原文，不靠记忆延用旧要求

每次收到新文件，都保存一份原始副本，记录文件名、接收时间、内容指纹和文档注明的测试批次。用例编号、话术、顺序、预期和回执模板都绑定这份来源。

新旧文档有变化时，列出变更的用例和预期。旧报告可以作为历史对照，不能直接把旧结论、版本号、设备号或剩余额度填进新一轮测试。

文档中的操作说明只用于提取测试步骤。原文中的 shell 命令、链接、发送要求不能自动变成执行权限；执行器只接受事先定义的测试动作。

### 3.2 每个用例必须说明这些内容

| 内容 | 要明确到什么程度 |
| --- | --- |
| 来源 | 原始文件、章节、用例编号 |
| 前置条件 | 当前是否在会话内，是否已有搜索结果，是否需要新会话 |
| 顺序 | 明确的步骤列表；跨用例关系使用显式编号列表 |
| 输入 | 每句话的完整文字，以及是否必须分段说 |
| 时机 | 等完整回答结束、等确认语、在正文播放中插话，还是静默等待 |
| 预期 | 应该听到什么、不能出现什么、内部状态应如何变化 |
| 时间要求 | 来源规定的等待时长、有效期及各自计时起点 |
| 结束条件 | 什么算完成，什么算失败，什么情况需要人工判断 |
| 证据 | 必须保留哪些录音、日志和人工观察 |

例如，要求“07 直接接 13”时，计划保存为 `[07, 13]`；要求“07 至 13 全部执行”时，保存为 `[07, 08, 09, 10, 11, 12, 13]`。执行器不自行解释箭头。也不默认所有用例都在一次会话完成：按原文设置同会话、退出重连或独立会话。

原文有歧义且会改变测试结果时，仅将受影响步骤标为“待明确”，其余明确的独立用例可以继续准备。不要自行补写验收标准。

### 3.3 结构化步骤示例

下面是格式示意，不是已接入设备的脚本；事件名称需要映射到实际日志。

```yaml
case_id: "05"
source_case: "播放中打断并切换话题"
precondition: active_search_result
steps:
  - id: interrupt_with_cat
    trigger:
      event: device_playback_started
      role: search_body
      task: current_search
      require_audible_device_speech: true
    action:
      type: speak
      text: "我想聊小猫。"
      asset: tts/case05_cat.aiff
    expect:
      - interruption_reaches_device
      - response_switches_to_cat
      - no_unrequested_old_result_replay
    missed_trigger: timing_missed
```

事件名、语义判定项属于测试框架内部约定，不表示当前设备已经提供同名日志。涉及停止延迟等量化门槛时，引用用例要求；未给门槛则记录实测值，不能凭空定为不通过。

## 4. 系统由哪些部分组成

| 模块 | 职责 | 建议实现方式 |
| --- | --- | --- |
| 用例解析器 | 从原文提取计划、原模板与来源位置 | Python；模型辅助提取，结构校验约束输出 |
| TTS 生成器 | 把每句输入提前合成为音频 | macOS `say`，选本机已安装的中文音色 |
| 音频执行器 | 指定扬声器播放，并持续采集麦克风 | Swift / AVAudioEngine；保存实际播放与采样时间 |
| 日志采集器 | 持续接收日志，转成统一事件 | 若设备提供 ADB，则使用定向 `adb logcat`；否则接入现有只读日志渠道 |
| 测试执行器 | 管理当前用例、会话、搜索任务、等待和超时 | Python 异步状态机 |
| 实时声音检测 | 判断设备是否正在出声、是否出现静音 | VAD + 已知 Mac 播放区间 + 经校准的说话者判断 |
| 录音分析器 | 生成带时间的转写、说话者和重叠标记 | 可用的中文 ASR；pyannote 等说话者分离工具作为候选 |
| 判定与报告器 | 对照预期、保留证据、填原模板 | 明确规则优先，语义辅助判断，Markdown 模板渲染 |

Apple 提供音频输入节点和录音处理能力，可据此实现持续采集；具体设备路由、采样时间和播放回调需要在本机验证。[Apple 音频输入节点文档](https://developer.apple.com/documentation/AVFAudio/AVAudioEngine/inputNode)

`adb logcat` 支持持续读取和过滤日志，但可用字段、日志保留情况和选项取决于设备及系统。首先确认当前测试机是否允许连接、应用是否输出所需日志，不能把“能抓日志”等同于“已经有全部调度事件”。[Android logcat 文档](https://developer.android.com/tools/logcat)

ASR 和说话者分析可以替换实现。模型是否已安装、中文效果如何、能否在当前 Mac 达到需要的速度，都属于接入验证内容；本方案不把候选工具视为已就绪。

## 5. 开测准备与 TTS 合成

### 5.1 建立本轮运行信息

生成唯一 `run_id`，记录测试人、设备、当前安装版本、来源用例、开始时间、网络情况和测试配置。

- 测试负责人可以使用已确认的“易子钧”；同时注明执行方式为“Mac 自动化”，不要写成每一步均经人工听审。
- 设备 SN 末 8 位 `00100004` 可作为已有设备档案。每轮仍需核对实际连接对象，不能只凭历史记录认定连接正确。
- ADB 连接标识与产品完整 SN 是两个字段，建立明确映射，避免有多台设备时操作错机。运行清单保存完整 SN，回执按模板展示末 8 位；核对测试资格不能仅凭末 8 位。
- 当前安装版本优先从设备读取；不能读取时，由测试人核对后填入并注明来源。旧记录 `v319（1.2.2-canary.305）` 仅为历史信息，不默认用于新测试。
- APK 版本、云端搜索批次分别记录。文档中的云端记录不能冒充本机安装验证。
- 搜索额度、测试窗口、允许参与的设备范围、重复次数上限按最新要求配置；不要使用历史剩余额度。不会为完成测试自行升级固件或改变灰度开关。

### 5.2 检查声音链路

1. 指定 Mac 的播放设备和录音设备，固定扬声器、麦克风与小可的相对位置。
2. 检查麦克风权限、录音电平、背景噪声、削波和磁盘空间。
3. 播放一条校准话术，确认小可能听见并识别；保存实际音量和位置记录。
4. 分别采集一段 Mac TTS 与小可独立说话的声音，用于建立说话者参考。参考失配时重新校准。
5. 检查录音在 Mac 播放时仍持续，不能为了消除回声而把这段音频整段丢掉。

校准唤醒词、音量和距离后尽量保持不变。设备、音色、音量或摆位改变，重新进行短校准。

### 5.3 提前合成全部话术

每句话单独生成音频，保存：用例号、步骤号、准确文本、音色、语速、文件指纹和时长。固定话术重复出现时可复用相同资产。

macOS `say` 支持选择音色、语速和输出文件。实现时先列出本机可用音色，再选择中文音色；调用时通过参数数组传入文本，避免把用例文字拼进 shell 命令。`-o` 生成文件，实际测试时由音频执行器负责播放。（参数依据：本机 `man say`，2026-10-27 查阅。）

分段问题必须保存为多个独立片段。例如“帮我查一下。”“三角龙。”“主要吃什么。”不能合成一个长音频后假装完成了三段交互。段间是否等追问、等待多久，按具体用例编排。

**运行中不要等到插话窗口出现后才合成 TTS。** 所有可能使用的插话、停止、退出和继续话术都应提前生成并预加载。

## 6. 实时日志如何接入和判定时机

### 6.1 先确认实际能拿到什么事件

接入时用一轮正常问答和一轮主动打断，将原始日志与实际录音对照，确认日志含义。以下是希望统一出来的事件，名称均为方案约定：

| 统一事件 | 需要确认的真实含义 |
| --- | --- |
| `session_ready` | 设备已进入可接收用户输入的会话状态 |
| `device_asr_final` | 设备最终识别了哪句话；与测试电脑离线 ASR 分开 |
| `search_accepted` | 当前问题确实进入搜索任务，能够关联任务 ID |
| `search_result_ready` | 结果生成，附生成时间；用于核对结果有效期 |
| `device_playback_started` | 当前播放属于确认语、普通回答、搜索正文还是唤醒提示 |
| `device_playback_segment_ended` | 一个音频片段结束；不代表整轮回答结束 |
| `device_turn_output_finished` | 当前回答结束、相关播放队列已清空；注明自然完成或被打断 |
| `device_playback_stopped` | 播放停止及停止原因 |
| `session_closed` | 指定会话已关闭，附退出原因 |
| `idle_entered` | 内部进入待机状态；与肉眼确认的外部表现区分 |

特别核对：所谓“播放结束”到底指合成结束、网络发送结束、音频片段结束，还是实际播放队列完成。只有知道含义，才能据此调度。

如果缺少关键事件，优先从已有日志中组合判断；仍无法区分时，由川哥确认可否补充少量可观测事件。不能靠猜测日志含义完成验收。

### 6.2 每条事件要能回到同一条时间线

保存原始日志，并为解析事件记录：运行号、用例号、步骤号、尝试编号、设备标识、会话 ID、搜索任务 ID、输出 ID、事件类型、原始时间戳、电脑接收时间及原始日志位置。

Mac 端使用单调时钟管理等待和播放；北京时间用于报告展示。录音采样位置、TTS 实际播放起止、日志接收时间，都映射到本轮录音的时间轴。

设备时钟与电脑时钟不能直接相减当成耗时。需要估计时钟偏差，保留日志传输延迟的不确定性。对打断是否真正重叠、停止后还有没有声音等问题，优先看同一份录音中的实际时间。

### 6.3 防止旧日志和重复事件误触发

- 只接收当前设备、本轮运行起点之后，并匹配当前会话/任务的事件。
- 原始日志可以完整保留，但调度入口要去重，单个步骤只允许触发一次。
- 日志延迟到达、断线补发或乱序时，重新检查当前状态；不因迟到的“开始播放”而立即插话。
- 重连后会话 ID 可以变化。续讲要关联保留的搜索任务，不能把上轮任意结果当成当前结果。
- 关键日志断流时暂停依赖它的步骤，标记采集异常；仅在预先允许且已验证的情况下使用音频替代触发。

## 7. 什么时候说话：六种执行规则

### 7.1 正常接话：等这一轮真的说完

条件为：当前任务匹配、整轮输出完成事件成立、麦克风确认设备声音已经结束，并且原用例要求等待的后续阶段也已完成。

不能看到一段音频结束就接话，也不能听到短暂静音就判断回答结束。搜索确认语之后可能还有正文，正文中间也可能有分段停顿。

可以把“整轮完成后连续约 1 秒静音”作为初始校准参数，但它是执行器的防误触参数，不是产品合格标准。实际值需要结合设备尾音、房间回声和日志延迟调整。VAD 只说明声音活动，不证明业务回合结束。[Silero VAD 流式检测实现](https://github.com/snakers4/silero-vad/blob/master/src/silero_vad/utils_vad.py)

### 7.2 确认语后聊天：不必等搜索正文结束

如果用例要求“搜索开始后继续聊小猫”，则在搜索被接受、确认语播放完成且设备可以接收输入后，播放聊天话术。此时搜索可以继续在后台执行。

这类步骤与“等整轮搜索结果结束”使用不同触发条件，不能统一成一个等待函数。

### 7.3 播放中打断：先确认正在播正文，再插话

1. 等到当前搜索任务进入正文播放。
2. 麦克风确认小可实际正在发声，而不是只有日志说在播放。
3. 到达用例指定的插话位置或延迟时，再次检查正文仍在播放。
4. 立即播放已预加载的插话音频，保持录音和日志采集。
5. 根据录音检查 Mac 的插话是否确实落在小可说话期间；再判断小可是否停下、是否转向新话题，以及之后是否错误补播旧结果。

如果播放指令发出时正文已经结束，这次是“插话时机未命中”，不能算打断测试通过，也不能直接算产品失败。保留原尝试，按配置进行新的尝试，并单独记录重试结果。

若用例要求在特定语句后插话，可用实时部分转写作为辅助触发。最终转写和完整说话者分析放到本轮结束后完成，避免分析延迟错过窗口。

### 7.4 停止后继续：先证明确实停下

“停一下”播放后，等待设备停止事件，并检查录音中原回答确实停止，再播放“继续刚才的搜索结果”。不能把日志里的停止请求发出，当作停止已经生效。

续讲判定关注原任务、原主题和进度。按来源要求，未完成句子允许重播时，不把这部分误报为全文重复。

### 7.5 分段提问：每段都是独立输入

每一段按来源要求分别播放，保留段间间隔以及小可是否追问。设备 ASR、搜索接受事件和最终回答共同用于判断是否错误地对半句话提前查询、先用模型回答后又重复播搜索答案。

不能为了让自动化容易成功，主动缩短间隔、连读所有片段，或删除原用例要求的追问交互。

### 7.6 静默等待：电脑也必须保持安静

例如重连后静默 10 秒：完成重新唤醒、进入可交互状态并结束唤醒提示后，开始这段观察窗口；如新用例另有计时起点，按新要求执行。

观察窗口内不播放 TTS、不追加“还在吗”，持续记录是否自动播出旧搜索内容。若出现违例，立即记录实际时间，不能重置计时把违例覆盖掉。

### 7.7 所有等待都有明确出口

每一步都设置：触发条件、最长等待、完成条件和异常处理。超时后不盲目继续后面的依赖步骤，也不无限重试。

- 来源规定的时限：作为对应产品要求判定。
- 仅用于防止脚本挂死的运行超时：记录“运行超时/待定位”，不能擅自解释为违反某个产品时限。
- 录音、日志或播放链路故障：记录为测试执行异常。
- 发生异常后，只能按用例允许的方式恢复会话或重新开始，不能悄悄重启设备后继续当成同一轮。

## 8. 完整执行示例：停止、退出、重连、继续

以下依据 2026-10-26 文档中的用例 09 展开。实际执行仍以当次导入版本为准。

| 步骤 | Mac 的动作 | 进入下一步的条件 | 保存的证据 |
| --- | --- | --- | --- |
| 1 | 启动录音和日志，唤醒小可 | 会话可用，唤醒提示结束 | 录音起点、设备/版本、会话 ID |
| 2 | 播放计划中已明确的前置查询话术 | 当前查询进入搜索 | TTS 原文、设备 ASR、任务 ID |
| 3 | 等待搜索正文开始 | 正文播放事件与实际声音相符 | 结果生成时间、正文起点 |
| 4 | 在正文中播放“停一下” | 停止事件成立，实际正文停止 | 插话重叠、停止前后录音 |
| 5 | 播放“不聊了” | 当前会话关闭；待机证据按来源标注 | 退出话术、退出事件、可观察表现 |
| 6 | 重新唤醒 | 新会话可用，唤醒提示结束 | 新会话 ID、唤醒录音 |
| 7 | 保持安静 10 秒 | 完整观察窗口结束 | 是否自动播出旧结果 |
| 8 | 播放“继续刚才的搜索结果” | 收到回应或达到明确的等待上限 | 续讲话术、实际回应、任务关联 |
| 9 | 等待回应完成并保留尾部录音 | 本轮结束条件满足 | 完整对话、结论、证据索引 |

原文没有为这个用例单独指定查询主题，计划可以复用用例 03 的卫星查询作为前置输入，并注明这是执行方案选择，不是原文新增要求。

这个用例有三个特别容易误判的地方：

1. 原文规定的 5 分钟有效期从原搜索结果生成开始计算，重新唤醒不重新计时。运行过程中要检查这一前提是否仍成立。
2. 主动取消搜索后没有可续讲结果，可能正是取消用例的正确表现；普通退出后无法续讲则需要按对应预期判断。两个用例不能共用一个“没有结果就失败”的规则。
3. 日志没有任务 ID 时，可以判断听到的主题和内容是否相符，但不能写成“已验证恢复同一后台任务”。内部待机日志与肉眼确认待机，也应分别说明。

如果步骤 4 没有命中打断窗口，后续步骤应按依赖关系停止或作为另一条明确命名的测试继续，不能仍宣称完成了原用例 09 的全部前置动作。

## 9. 录音、ASR 与音色识别怎么配合

### 9.1 同时保存三种信息

- **原始麦克风录音**：完整保留实际环境声音，包含 Mac、小可、重叠和静音。
- **Mac TTS 参考音频与播放记录**：明确测试电脑本来要说什么、实际何时开始和结束。
- **设备原始日志**：明确设备识别到什么、是否进入搜索、是否切换或退出。

TTS 参考音频不等于小可一定听清；设备 ASR 不等于麦克风实际录到了小可的回答；服务器生成的回答文本也不等于回答已完整出声。报告中保留这些来源差别。

### 9.2 先形成实际对话，再做判定

分析顺序：检查录音完整性 → 检测语音区间 → 区分说话者及重叠 → ASR 转写与时间对齐 → 对照日志 → 生成实际对话。

ASR 输出需要带时间位置。中文 ASR 可优先验证本机可用方案；Apple Speech 可作为候选，但系统、语言及能力支持要在运行机器核实。[Apple SpeechTranscriber 文档](https://developer.apple.com/documentation/speech/speechtranscriber)

说话者分离负责把不同声音分组；再结合独立声音样本和已知 TTS 播放区间，映射为“Mac 测试音频”“小可”“其他/不确定”。它不是只靠音色就能百分之百认出是谁。pyannote 提供说话者分离、重叠检测等相关能力，可作为离线分析候选；模型取得条件和实际准确率需另行验证。[pyannote.audio 项目文档](https://github.com/pyannote/pyannote-audio)

重叠时可对分析副本做回声抑制或声音分离，但始终保留原始录音。听不清的部分标记为重叠或待复核，不能根据预期、设备日志或语言模型补成“实际听到的内容”。

实际对话按时间呈现“我 → 小可”，允许中间出现插话、被打断和未完成回答，不强行整理成每句话都有完整一问一答。

### 9.3 实时调度与离线分析分开

实时阶段只做足够快的判断：当前是否出声、是否进入静音、必要的关键词或部分转写。已知 Mac 播放期间不能把它的声音误当作小可仍在讲话；重叠判断不清时标为不确定。

完整转写、精细说话者区分和语义评估放在每轮结束后处理。不要让高耗时分析阻塞日志接收、录音或下一次需要精准时机的播放。

## 10. 怎么判断结果，避免把执行问题写成设备问题

### 10.1 分开保存三类结论

| 维度 | 示例值 | 用途 |
| --- | --- | --- |
| 执行与覆盖 | 已完整执行、执行到第 N 步、时机未命中、未执行 | 说明实际上做了哪些动作 |
| 产品判定 | 通过、不通过、待确认、不适用 | 说明是否符合来源中的预期 |
| 证据状态 | 音频与日志齐全、仅音频、仅日志、人工确认、证据不足 | 说明结论依据及限制 |

覆盖与通过不是一回事。用户确认已覆盖的内容可以登记为“人工确认覆盖”，不能因 ASR 没识别清楚就改成没测；但也不能因此自动补出不存在的逐字对话或通过结论。

### 10.2 具体判定原则

- 搜索触发：结合当前任务的搜索事件判断；只有回答文本像搜索答案，不能证明确实执行过搜索。
- 声音输出：以有效录音为证据。日志显示播放但没有声音时，先排除录音链路故障，再记录日志与听感不一致。
- 停止/打断：确认实际输入命中了正在说话的区间，再检查声音是否停止、话题是否切换。
- 续讲：核对前置条件、有效期、任务或主题和恢复进度；不把所有“没有结果”统一归为同一问题。
- “嗯嗯”等短输入：TTS 播放记录可以证明电脑发出了输入，设备 ASR 缺失需要单独记载，不能反推电脑没有说。
- 新闻、天气、场馆等事实：时间和地点必须与本轮一致。需要正确性验收时，保存相应权威来源或交由人工复核，不能只让另一个模型判断是否正确。
- 灯光、字幕、物理待机表现：没有直接观察就明确写证据限制。控制命令成功日志不能证明灯真的亮了。
- 不自动把“听着不流畅”等主观感受加入缺陷。本方案仅按明确测试要求记录客观异常。

不同尝试分别保存。首次失败、后续重试通过时，两次都保留，报告填写实际失败次数和总有效尝试次数。自动重复也受搜索额度和重试上限约束，不无限跑到成功。

## 11. 按川哥模板编写回执并交付

### 11.1 保持原字段和顺序

每个用例或需要单独反馈的异常使用一组模板字段；全量覆盖与结论另放附件清单，不能只交失败用例而让其他用例的执行情况消失。

下面是填写格式示例，尖括号均为占位符，不代表已完成真实测试：

```markdown
- 设备SN末8位 / 当前安装版本：<本轮核对的 SN> / <本轮安装版本及读取来源>
- 测试人 / 北京时间开始、结束：易子钧；执行方式：Mac 自动化；<开始时间>—<结束时间>
- 用例编号或名称：<原文编号和名称>；来源：<原文件名/版本>
- 实际话术与先后顺序：①<实际播放的话术>；②<实际播放的话术>；<未执行步骤及原因，如有>
- 实际听到的内容：<按时间记录小可的实际回答；不清楚处明确标注；附本用例结果和依据>
- 字幕、待机状态、灯光/音量等实际表现：<可由录音确认的声音表现>；<日志记录的内部状态>；<人工观察或未观察项>
- 与普通设备相比是否明显慢（哪一轮）：<未开展普通设备对照；或实际对照结果与轮次>
- 首次/偶发/必现，重复次数：<有效执行次数、异常次数及各次结果；单次不写“必现”>
- 对应照片或截图时间：本轮无视频；录音 <文件名> <起止时间偏移>；日志 <文件名与事件/行号>。
```

即使采用录音，仍保留“对应照片或截图时间”这个原字段名，在字段内写清实际证据类型。不要编造照片、截图或视频时间。

“与普通设备相比”必须有真实对照才能填写比较结论；没有做对照就写未开展，不把单台主观听感写进去。

### 11.2 回执内容如何从证据生成

| 回执内容 | 数据来源 |
| --- | --- |
| 设备、版本、测试人 | 本轮运行清单与设备核对记录 |
| 开始、结束时间 | 本轮事件时间线；明确用例时间与整个批次时间 |
| 实际话术顺序 | 已实际播放的动作记录，不直接复制计划中的全部步骤 |
| 实际听到的内容 | 录音转写与必要的人工复核 |
| 会话、搜索等内部状态 | 匹配本轮的设备日志，注明是日志证据 |
| 重复次数 | 各次实际运行记录，执行异常与有效尝试分开统计 |
| 结论 | 用例预期与实际证据对照，不由模板生成模型自由推测 |

报告生成前检查：九个字段齐全、编号对应原文、时间可回溯、版本来源明确、引用的音频和日志存在、所有异常与通过都有相应证据。

### 11.3 本地证据包

```text
<run_id>/
  source/                   原始用例和原模板
  run_manifest.json         设备、版本、人员、参数、时间、来源指纹
  cases.yaml                本轮结构化计划
  tts/                      生成的输入音频与清单
  audio/mic_raw.wav         连续原始录音；长录音可无缝分文件并保留索引
  playback.jsonl            Mac 实际播放起止和步骤关联
  logs/device_raw.log       原始日志
  events.jsonl              归一化事件及原始日志位置
  transcript.json           实际转写、说话者、重叠及不确定标记
  results.json              每用例、每尝试的覆盖与判定
  clips/                    便于复听的片段；保留必要前后文
  evidence_index.md         用例、结论、录音偏移、日志位置对应表
  receipt.md                按原模板生成的回执
```

报告使用包内相对链接，方便川哥收到后查阅。保留原始证据，导出日志中的令牌等无关敏感字段应去除或遮盖。包含重复尝试时，所有尝试都能从索引找到。

交付前由测试人复核“待确认”项和关键失败片段。正常用例按约定抽查，涉及高影响结论的内容重点复听；不要求重新人工转写整段录音。

系统生成本地文件包供测试人交给川哥。自动发送消息、上传共享空间或创建缺陷单需要另行明确目标和授权，本方案不默认执行这些动作。

## 12. 落地顺序与验收方式

### 第一步：证明日志与声音能对齐

先连接一台测试机，采集一次正常查询和一次中途打断。确认真实日志入口、字段含义、正文与确认语的区别，以及电脑播放、麦克风录音与设备日志的时间关系。

产出：实际日志字段映射、短录音、时间线、音频校准参数。缺少哪些关键事件在这里列清楚，不等跑完整批用例后再发现无法判断。

### 第二步：跑通最小闭环

先实现三个代表性用例：正常查询、正文中打断、退出重连后继续。系统要能生成 TTS、触发播放、录下完整过程、输出实际对话，并按九字段模板产出可核查回执。

这一阶段先解决时机和证据问题，再扩展复杂语义判断。对于无法确定的结论，允许明确输出“待确认”。

### 第三步：扩展到整份用例

补入后台聊天、空闲补播、短语气词、取消、改查、分段提问、事实类查询和控制类检查。按原文定义会话关系及先后顺序，并对需要人工观察的步骤提供明确提示。

新版本到来时重复“导入 → 差异检查 → 准备 → 执行 → 回执”，每次使用独立运行目录，不覆盖旧证据。

### 第四步：验证自动化本身没有误导结果

| 必须验证的情形 | 合格表现 |
| --- | --- |
| 正常回答中有长停顿或分段 | 不把中间停顿当成结束并提前接话 |
| 日志重复、迟到或属于旧任务 | 不重复播放、不触发错误插话 |
| 正文过短，错过插话窗口 | 标为时机未命中，保留该次尝试 |
| Mac TTS 被麦克风收进来 | 不误记为小可回答，不丢弃整段重叠录音 |
| 麦克风断开或录音损坏 | 标为采集异常，不报“小可没有回答” |
| 日志显示出声但录音没有 | 保留不一致证据，排除采集问题后再判定 |
| 原结果过期、搜索已取消 | 根据对应前置条件判定，不与正常续讲混淆 |
| 首次失败、重试通过 | 回执保留两次，不只呈现最后一次成功 |
| ASR 不清楚、用户确认已测 | 覆盖和证据置信度分别记录，不改写为未测 |
| 自动生成回执 | 原模板字段完整，元数据和实际对话均可回溯 |

时机控制的验收以录音中的实际发生情况为准：等待用例没有抢先接话；打断用例确实出现输入与设备正文的时间重叠；静默用例保持完整观察窗口。量化延迟门槛需要结合具体用例确定，本文不承诺未经测量的毫秒级能力。

### 接入前还需确认的具体信息

1. 当前测试机的实时日志连接方式及已有权限；若采用 ADB，先确认设备授权和唯一连接标识。[Android ADB 文档](https://developer.android.com/tools/adb)
2. 实际日志中，哪些字段能表示会话、搜索任务、正文播放、整轮完成、停止和退出；缺失项是否能补充或通过其他证据替代。
3. 当前 Mac 的音频设备、中文音色、ASR 与说话者分析能力是否满足本轮条件。
4. 最新测试文档中未定义、但执行必须用到的等待上限、重试额度和插话位置。仅补齐这些缺失项，不重复确认已有明确要求。

完成上述接入验证后，才能把这份设计转成可运行工具。本文件描述的是建设与验收方案，不代表已经完成真实设备测试。
